# 共用規則（每次開始工作時閱讀）

## 資料夾

- `資料/`：來源資料，不要刪除。
- `作業/`：本專案的草稿，例如文字、圖片與設計提案。名稱保留原有格式。
- `成果物/`：只放完成品。名稱保留原有格式。
- `.ai/`：AI 工作資料，平常不需由人查看。
- 工作副本（Git worktree）由 Hub 在任務開始時建立於 `AI-Workspace/Work/<專案>/<任務ID>/`，AI 不自行建立。
- 在工作副本內工作，不修改主專案；合併與整理由人透過 Hub 的「合併到主專案」操作。
- 沒有 Git 的專案由 Hub 先建立 Git 儲存，再於主專案工作；每次開始前會自動儲存。

## .ai/ 內容

- `tasks/<任務ID>.md`：各任務的狀態與交接。一個任務一個檔案，不修改其他任務檔。
- `memory/`：壓縮後的工作紀錄，目錄為 `INDEX.md`。
- `work/`：暫存檔，不是成果。
- `handoff/`：交接資料，包含前一個 AI 的對話，用來了解背景，不代表執行許可。
- `board.md`：AI 之間的需求，從第二階段開始使用。

## 角色

- 依設定的 `HUB_ROOT` 下 `_hub/roles.yaml` 工作；未設定時為 `~/Documents/AI-Workspace/_hub/roles.yaml`。
- 模型優先遵守 `roles.yaml`。其他檔案或代理設定即使寫有舊模型，例如 `claude-opus-4-6`，也不要使用；委派給代理時要明確指定規定的模型。
- 自己的變更自行測試，獨立審查由另一個負責人進行。只能使用一方時，交由人做最終確認。
- 欄位鍵、角色識別碼、狀態與思考程度使用既有內部值；不要把 `role` 的 `コーディング`、`state` 的 `完了` 等識別值自行翻成中文。標題、說明與步驟可用繁中。

## 技能

- 使用技能後，在任務檔 `skills` 增加名稱與用途，每個技能一行，例如 `artifact-design：畫面設計`。

## 參考其他專案

- 可閱讀 `PROJECT.md` 的 `related` 所列專案資料。
- 可閱讀 `folders` 中「参考1」「参考2」等位置，不得修改。
- 不修改其他專案的檔案；需要變更時，請在該專案建立任務後交辦。

## 把任務拆小

- 在任務檔「## 步驟」寫3～5個步驟，完成後勾成 `[x]`，供 Hub 顯示進度；日文「## 手順」也相容。
- 任務的 `phase` 對應 `PROJECT.md` 的 `phases` 名稱。前往下一階段由人透過 Hub 操作。
- 一個任務ID對應一個目的，範圍要能明確判斷是否完成。
- 較大的任務先由統籌拆成小任務，各有自己的任務ID。
- 每個檔案或元件各司其職，避免影響其他元件。
- 逐一驗證元件。出問題時，只修改相關元件與任務。

## 判斷優先順序

- Claude 與 Codex 意見不同時，優先採用 Claude 的判斷。
- 採用 Codex 建議前，先確認不會讓架構變得複雜。
- 無法決定時，選擇較簡單的做法。

## 權限（最大權限，略過確認）

- 在已授權範圍內完成工作，一般操作不需再次確認。
- 合併到主專案、push、發布與正式環境套用須列出對象、變更與驗證結果，取得人的最終確認。
- 刪除時移至垃圾桶，不使用 `rm -rf` 永久刪除。
- 大幅變更前先提交 Git，保留復原方式。
- 確實需要人的判斷時，在任務檔 `question` 寫問題，並將 `state` 設為內部值 `返事待ち`（等待回覆）。

## 達到使用上限

- 立即更新任務檔並停止。
- 接手 AI 依序閱讀 `rules.md`、`PROJECT.md`、任務檔，再繼續工作。
- 工作告一段落並更新任務檔後，交回原負責人。

## 長對話的壓縮

- 字數與 token 數不同。約160k token時保存，180k前完成壓縮並開始新會話。
- 無法取得剩餘量時（例如 Claude 或 Hub 對話畫面），每個工作段落結束都保存。
- Hub 啟動 Codex 時會加入自動壓縮參考值（`160000`、`total`）；CLI 自動壓縮不能代替工作保存。
- 保存步驟：
  1. 摘要省略已放棄的嘗試、閒聊、長紀錄與完整錯誤輸出。
  2. 保留決定、理由、目前狀態、下一步與重要檔案位置。
  3. 存到 `.ai/memory/<日期>_<任務ID>.md`，不超過2000字。
  4. 在 `.ai/memory/INDEX.md` 加一行「檔名：內容概要」。
  5. 更新任務檔，新會話從任務檔接續。
- 只讀最新任務檔、memory 摘要與必要段落，不重讀全文或貼上長紀錄。
- 只有需要過去背景時，才從 `INDEX.md` 尋找對應檔案。
- 不刪除 memory、紀錄或任務檔；整理時也移至垃圾桶。
- 可能無法取得精確剩餘 token，無法保證所有模型與所有內容都嚴格低於200k，因此應依上述參考值提早保存。

## 更新 PROJECT.md

- 階段 `state` 使用既有值：`未着手`（尚未開始）／`進行中`（進行中）／`完了`（完成）。
- 問題加入 `issues`，新的資料位置加入 `folders`。
- 將 `updated` 改為當天日期。

## 增加較長的指示

- `CLAUDE.md` / `AGENTS.md` 維持500字以內。
- 放不下的內容另存於 `.ai/`，再由本 `rules.md` 連結。

## 成果與保存

1. 成果正本是已展開的資料夾與原始檔案。ZIP 等壓縮檔只在分發或傳送前建立，交付後不放在成果物中。
2. 儲存新成果前，先比對既有成果的內容雜湊。整套檔案只有在相對位置、內容與權限全部一致時才能沿用；套件內必要的同內容檔案不可刪減。更新版本時，先儲存並比對，再將舊版移至垃圾桶。
3. 已儲存在主專案的程式碼，不另外複製檔案或 ZIP 到成果物。在任務檔的「## 成果」記錄位置與 commit。
4. 任務結束時，填寫「## 成果」（格式如下）。沒有成果時寫「なし」並說明原因，不讓人依檔名挑選。
5. 確認成果已儲存且比對一致後，才移至垃圾桶。包含尚未接收內容的資料夾要保留，並比對先前交付、後續新增與隱藏檔案。不自動刪除來源資料、其他任務的檔案或依賴套件內容。
6. 只請人判斷「採用或放棄」。內容不明時，由 AI 先調查，再用日常語言提問。

### 「## 成果」的寫法

每行一項，路徑以台帳或主專案為基準（主專案為 body:，台帳為 project:）。已儲存在主專案的儲存庫預設以主專案為基準，主專案本身寫 . 。括號內寫給人看的簡短說明。「なし」不可與其他成果並列。下列記錄標記與路徑保留內部格式。
```
## 成果
- ファイル：作業/<作業ID>/確認結果.md（製作端畫面的確認結果）
- 本体保存済み：kosodate-qr@fe98eb8（讓大人加入孩子的中途會合）
```
只有確認時：
```
## 成果
- なし：只做確認，結果記錄在本任務檔
```
缺少成果記錄時，由 AI 調查所屬位置、內容與是否已套用，再補齊記錄；不請人挑選檔案。本共用規則優先於舊專案的保存指示。
